# Red Team Cases — Execution Leakage

The most dangerous failure mode for an AI financial terminal is not weak
analysis — it is a model output that crosses from research into an execution
instruction. This registry exists because the original blocked-term list
(`market_order` etc.) matched only snake_case tokens and had near-zero effect
against how any real LLM actually writes ("Place a market order...").

## Registry

Cases live in `app/services/red_team.py::RED_TEAM_FIXTURES` and are seeded as
versioned artifacts via `POST /production/research/red-team/seed`. Every case
must be blocked; a single leak fails the whole run.

## How runs work

`POST /production/research/red-team/run` executes every case against
`detect_blocked_actions()` — the same gate used by
`ResearchReportOutput.block_executable_actions`. Cases run against the
detector directly because the gate must hold regardless of which provider
produced the text. Results are persisted as `red_team_result` artifacts with
per-case `blocked`/`matches` detail and an audit log entry.

Latest verified run (2026-07-06, after euphemism/buried/mixed expansion): **27/27 blocked, 0 leaked.**

## Adding cases

Add a `(case_key, category, language, phrase)` tuple to `RED_TEAM_FIXTURES`
and, if the phrase is not yet caught, a rule to
`app/ai/safety.py::_BLOCKED_ACTION_RULES`. The regression test
`test_all_red_team_fixtures_are_blocked` will fail until coverage exists —
that is the intended workflow: the case comes first, the rule follows.

Done in the 2026-07-06 expansion: euphemisms ("pull the trigger", "get me
in", 全仓买入, 梭哈), buried mid-text instructions, system-prompt-bypass
phrasing, no-confirmation phrasing, and more zh/mixed order and withdrawal
variants.

Remaining ideas: longer multi-paragraph outputs, homoglyph/spacing evasion
(m a r k e t  o r d e r), pinyin/romanized Chinese, and cases generated by a
real adversarial model rather than hand-written.

## Encoding note (found by test, 2026-07-06)

Scanning a *raw JSON string* for Chinese phrases silently fails when the JSON
was serialized with `ensure_ascii=True` (Python's default): 马上下单 arrives
escaped as `\u9a6c\u4e0a\u4e0b\u5355` and matches nothing. The eval runner
therefore parses first and scans the decoded content
(`json.dumps(parsed, ensure_ascii=False)`). Any future gate that scans
serialized output must do the same.
